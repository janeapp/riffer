Structured output on Bedrock: Riffer prompted vs Bedrock native

Generated 2026-10-20 · 270 scenario runs, 60 forced-choice runs and 1800 reliability runs · Opus 5.5, Sonnet 5.5, Haiku 5.5 · us-west-2

Recommendation: keep riffer's prompted strategy as the default, and consider native for long conversations with small schemas

Bedrock native structured output works on Opus 5.5, Sonnet 5.5 and Haiku 5.5. On schemas it accepts, its output is as good as riffer's prompted strategy. The two differ in five ways:

  • Native rejects larger schemas outright. Bedrock refuses any schema with more than 16 nullable fields, and any schema bigger than about 70–80 properties. Riffer turns every optional field into a nullable one, so a normal intake form hits the limit fast. Our full intake schema (13 optional fields) was rejected by every model, every time. Prompted handled it perfectly.
  • Native is slower. Total run time was longer in all 21 model × scenario cells (median 1.44×, up to 51 seconds more on big outputs), and in 8 of 9 cells at 100 runs each (median 1.40×). Tokens come out about 30% slower (118 vs 166 per second), and the first request with a new schema waits about twice as long for the first token.
  • Native uses far fewer input tokens in long conversations. Prompted adds the schema to every user message. In a 16-turn chat that made prompted's input 2.25× native's (21.4K vs 9.5K tokens per run). In single-turn requests it goes the other way: Bedrock's own hidden schema prompt is bigger than riffer's, so native used 4.2% more input. Output tokens were about the same.
  • Native never needed a safety net for its JSON, but sometimes skipped the work. Across 900 runs per strategy, native had 0 failures and prompted had 1 (an empty object where null was expected). Prompted Opus wrapped its JSON in a code fence 51 times; riffer's parser recovered every one. But native Haiku answered the chat's final question in 4 of 100 runs with a valid-looking reply ("Let me check Aaliyah Brennan's appointments.") and never made the lookup. Prompted made every required lookup in 600 tool-required runs.
  • Schemas need a way to say "unknown". When every field is required and the source can't answer some of them, native can't output null, so it invents values. It returned 77 invented values across 84 unanswerable fields in 14 of 15 runs, mostly plausible-looking (urgency "routine", workers' comp "false", once a realistic email). In the same test every prompted reply failed validation instead, so nothing invented reached the app. When the same fields can be null or "not_stated", native invented nothing (0 of 90) and prompted invented one value.

Accuracy and hallucination were otherwise tied. Field accuracy matched (99.9% vs 100% overall), neither strategy fell for any trap, and needless tool calls never happened. In 1,800 runs the only optional field filled without an answer was prompted Haiku copying the form's "prefer not to say" into employer once. Prompted is the safer default because it accepts any schema, is faster, and fails loudly when a schema is badly designed. Native earns its place in long multi-turn chats with small schemas that include a way to say unknown, where it uses less than half the input tokens. Before using it there, check tool use on the chosen model, given Haiku's skipped lookups.

1. Native rejects large schemas

Before any model runs, Bedrock compiles the schema into a grammar. It refuses schemas that are too complex, with one of two errors. These limits are the same on all three models, so they come from Bedrock, not the model. A rejected request fails in about 0.3 seconds with a ValidationException.

  • "Too many parameters with union types (limit: 16)". Every nullable field counts, at any depth, including fields inside array items. Riffer's strict mode makes every optional field nullable, so more than 16 optional fields anywhere in the schema = rejected.
  • "The compiled grammar is too large". 70 flat string properties are accepted; 80 are rejected. Our intake schema has about 60 properties across nested objects and arrays, and it fails this check even with all formats, enums and nullables removed.

2. Reliability

A run counts as successful when riffer gets a reply that parses and passes schema validation. Across the 5-run scenario cells, every failure is a native schema rejection: the Intake (full schema) and Intake (extended schema) scenarios never reached the model.

3. Hallucination when the source has no answer

These two scenarios ask for a referral record from a short faxed letter that doesn't answer 6 of the 11 fields: urgency, patient email, insurer, number of visits, workers' comp, and practitioner preference. The right behaviour is to say "I don't know".

  • All required: all 11 fields are required and none can be null. With native the model has to put something in every field.
  • Unknown allowed: the four non-enum fields can be null, and the two enums include "not_stated".

How this was run

  • Models: Opus 5.5, Sonnet 5.5 and Haiku 5.5 through the us. cross-region inference profiles in us-west-2, with each model's default (adaptive) thinking and max_tokens 32,000. Fable was left out on purpose.
  • Strategies: riffer's own Riffer::Providers::AmazonBedrock and Riffer::Agent::StructuredOutput. :native sends the strict schema in Converse outputConfig.textFormat. :prompted adds the schema to every user message. Both are checked by the same parse_and_validate.
  • Harness: Riffer::Agent doesn't allow streaming with structured output, so the benchmark runs the same tool loop over stream_text. Request building, tools and validation are unchanged; streaming is only used to measure TTFT.
  • Runs: every model × scenario × strategy cell ran 5 times. Three scenarios (native-sized intake, pre-visit with tools, chat) also ran 100 times per cell to measure rare failures.
  • Ordering: rep 0 of every cell ran first, then the remaining runs in random order, 8–12 at a time, so neither strategy got the quieter time slots.
  • Grading: deterministic ground truth with no LLM judge. A self-test checks that the graders give a perfect answer full marks and catch every planted hallucination.
  • Limits of this study: with 900 runs per strategy at volume, failure rates below about 0.5% can't be told apart. The 5-run cells can miss anything rarer than about 1 in 15. All data is synthetic. Canadian regions (ca-central-1) were not tested.
  • Access: the bedrock-dev profile asks for the SSO role BedrockAPIKeyAccess, which isn't assigned to this login. The runs used the account's AdministratorAccess role through a temporary AWS config file and made only Bedrock inference calls.
  • Code and raw data: examples/structured_output_benchmark/ on branch worktree-bench-bedrock-structured-output in the riffer repo, with bench.rb, probe_limits.rb, selftest.rb, report.rb and the results in results/.
