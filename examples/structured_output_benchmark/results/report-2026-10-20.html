Structured output on Bedrock: Riffer prompted vs Bedrock native

Generated 2026-10-20 · 240 runs plus 30 forced-choice runs · Opus 5.5, Sonnet 5.5, Haiku 5.5 · 5 reps per cell · us-west-2

Recommendation: keep Riffer's prompted strategy as the default

AWS has turned native structured output back on, and it works on Opus 5.5, Sonnet 5.5 and Haiku 5.5. Where it runs, its output is as good as ours. But it is not a drop-in replacement:

  • It rejects our larger schemas outright. Bedrock refuses any schema with more than 16 nullable fields, and any schema bigger than about 70–80 properties. Riffer turns every optional field into a nullable one, so a normal intake form hits the limit fast. Our full intake schema (13 optional fields) was rejected by every model, every time. Prompted handled it perfectly.
  • It makes things up when a required field has no answer. Native decoding can't output null, so it fills the gap: in 14 of 15 runs it returned a "valid" object with 77 invented values across 84 unanswerable fields. 57 of those looked like real data (urgency "routine", workers' comp "false", and in one run a realistic email, naomi.lindqvist@example.com). One run got stuck writing a fake email address until it hit the 32,000-token limit. With prompted, every one of those runs failed validation instead, so no invented value reached the app.
  • It is slower. Total run time was longer in every model × scenario cell (median 1.47×, about 5 seconds; up to 51 seconds more on big outputs). Tokens come out about 30% slower (118 vs 166 per second), and the first request with a new schema waits about twice as long for the first token.
  • On everything else, it's a tie. Both strategies returned 100% schema-valid output on every schema native accepted. Field accuracy was the same (99.9% vs 100%), there were no hallucinations on optional fields, and tool use was perfect: zero needless calls and zero skipped calls in 240 runs. Token usage was close too: native used about 4% more input tokens and the same output tokens.

Earlier we found that the prompted strategy gave fewer validation errors and fewer hallucinations. This run partly changes that picture. On schemas native accepts, native now has no validation errors either. The hallucination gap only shows up when a schema forces an answer the source doesn't have, and there it is large. Native could make sense for small, fully answerable schemas where its built-in guarantee is worth the extra latency.

1. Native rejects large schemas

Before any model runs, Bedrock compiles the schema into a grammar. It refuses schemas that are too complex, with one of two errors. These limits are the same on all three models, so they come from Bedrock, not the model. A rejected request fails in about 0.3 seconds with a ValidationException.

  • "Too many parameters with union types (limit: 16)". Every nullable field counts, at any depth, including fields inside array items. Riffer's strict mode makes every optional field nullable, so more than 16 optional fields anywhere in the schema = rejected.
  • "The compiled grammar is too large". 70 flat string properties are accepted; 80 are rejected. Our intake schema has about 60 properties across nested objects and arrays, and it fails this check even with all formats, enums and nullables removed.

2. Reliability

A run counts as successful when riffer gets a reply that parses and passes schema validation. Every failure in the main run is a native schema rejection. The Intake (full schema) and Intake (extended schema) scenarios never reached the model.

3. Hallucination when the source has no answer

This scenario asks for a referral record from a short faxed letter. All 11 fields are required, and the letter doesn't answer 6 of them: urgency, patient email, insurer, number of visits, workers' comp, and practitioner preference. The right behaviour is to say "I don't know". With native, the model can't output null for a required field, so it has to put something there.

How this was run

  • Models: Opus 5.5, Sonnet 5.5 and Haiku 5.5 through the us. cross-region inference profiles in us-west-2, with each model's default (adaptive) thinking and max_tokens 32,000. Fable was left out on purpose.
  • Strategies: riffer's own Riffer::Providers::AmazonBedrock and Riffer::Agent::StructuredOutput. :native sends the strict schema in Converse outputConfig.textFormat. :prompted adds the schema to every user message. Both are checked by the same parse_and_validate.
  • Harness: Riffer::Agent doesn't allow streaming with structured output, so the benchmark runs the same tool loop over stream_text. Request building, tools and validation are unchanged; streaming is only used to measure TTFT.
  • Ordering: rep 0 of every cell ran first, then the remaining runs in random order, 8 at a time, so neither strategy got the quieter time slots.
  • Grading: deterministic ground truth with no LLM judge. A self-test checks that the graders give a perfect answer full marks and catch every planted hallucination.
  • Limits of this study: 5 reps per cell, so failures rarer than about 1 in 15 per cell could be missed. All data is synthetic. Canadian regions (ca-central-1) were not tested.
  • Access: the bedrock-dev profile asks for the SSO role BedrockAPIKeyAccess, which isn't assigned to this login. The runs used the account's AdministratorAccess role through a temporary AWS config file and made only Bedrock inference calls.
  • Code and raw data: examples/structured_output_benchmark/ on branch worktree-bench-bedrock-structured-output in the riffer repo, with bench.rb, probe_limits.rb, selftest.rb, report.rb and the results in results/.
